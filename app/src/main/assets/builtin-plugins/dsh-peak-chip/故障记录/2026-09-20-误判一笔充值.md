## 1. 一句话结论

误判不是数据脏，是**判定规则把「余额单窗口净减少」的窗口判成了充值**，而这个规则成立的前提（本地下界 `low` 与余额变化 `delta` 覆盖同一个计费区间）在本机不成立 —— 余额结算是滞后的。

## 2. 判定规则原文（v3.2.0 `refresh()`）

```js
const increase = previous >= 0 ? round4(total - previous) : 0;   // Δ
const local = windowSpend(now);                                   // 本窗口的 low/high
const impliedTopUp = increase + local.low;                        // ← 关键
const topUp = impliedTopUp > TOPUP_EPS ? tierAtLeast(impliedTopUp) : 0;
```

设计意图（代码注释第 544–556 行）：
> 没有充值时可证明 `Δ + low ≤ 0` —— 那时 Δ = −本端消费，而 low 正是它的下界。所以只要 `Δ + low > 0`，就一定有钱进来。

两个放大器：

```js
const TOPUP_EPS = 0.009;                              // 噪声阈值 = 9 厘
const TOPUP_TIERS = [10, 20, 50, 100, 300, 500];      // 最低档 ⟨金额⟩元
function tierAtLeast(amount) { /* 返回 ≥ amount 的最小档位 */ }
```

`tierAtLeast` 的地板是 10 —— **任何大于 0.009 元的正残差都会被放大成 ⟨金额⟩元**。

## 5. 根因（三层，从表到里）

### 5.1 直接原因：唯一判据是 `Δ + low > 0`，它没有校验余额方向

规则只问「残差是否为正」，不问「余额是否变多」。而充值在定义上必须让余额变多。本窗口余额是**减少**的，仅凭这一点就该否决。

（注意：不能简单地加「`increase > 0` 才认充值」—— 设计上允许「充 10 花 12 → Δ=−2」成立。所以这条不是充分的修复，见 5.2。）

### 5.2 根本原因：`Δ` 和 `low` 描述的不是同一个计费区间

> **⚠️ 本节结论已被第 12 节的真充值观测修正。** 保留原文以记录判断过程。修正后的表述见 5.4。

- `low` 是**本窗口**（hh:mm:ss→hh:mm:ss）由 token 算出的本端消费下界；
- `Δ` 是**官方余额接口在这两次查询之间报出的差额**，而余额结算是**滞后/批量**的。

插件自己的账本 README 第 43 行已经写下了这个现象：

> 余额接口自身可能有延迟：实测**逐窗对不上、累计才对得上**，所以拟合要在小时级/天级复核

README 因此把拟合的粒度放到了小时/天级 —— **但充值推断仍然把这个逐窗 Δ 当成了精确量**。同一份文件里，一个已知滞后的信号被用在了瞬时不变式上。

本窗口的数据就摆在这里：余额只减了 A3，而本窗口仅保守口径就有 ⟨金额⟩、大胆口径 A37。也就是说

> **余额的下降幅度小于保守下界 `low`** —— 在「low 是真下界」的前提下这是不可能事件。

不可能事件发生了，只有两种解释：余额滞后（结算没跟上），或 `low` 不是真下界（价目/分桶偏差）。两种都指向**账本侧**，都不指向「有充值」。

### 5.3 放大机制：⟨金额⟩ 元的残差 → ⟨金额⟩元的主张

- `TOPUP_EPS = 0.009` 形同虚设（9 厘）；
- `tierAtLeast` 的地板是 ⟨金额⟩元，**最小可能的主张就是 ⟨金额⟩元**；
- 于是 ⟨金额⟩ 元的判定残差被放大 **40 倍**；
- 更糟的是 `baseBalance = round4(baseBalance + topUp)` —— 一旦判出，基准被**永久**抬高，当日剩余时间的「今日消耗」全部 +10。**没有任何回退路径。**

### 5.4 修正后的根因（真充值观测之后）

**充值入账是准时的（≤15.5 秒），所以根因不是「结算滞后几分钟」，而是判据没有信噪比概念。**

实测比值 `low / |Δ|`（余额侧反推的消费 vs 本地下界）：

| 窗口 | low / \|Δ\| |
|---|---|
| hh:mm（误判） | **⟨金额⟩** ← 唯一离群 |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |
| hh:mm（真充值窗口，low/implied） | ⟨金额⟩ |

稳态下两个量本身就差 **10~15%**。一个典型窗口消费 0.2~0.4 元，对应 **2~6 分钱的固有偏差**；而决策阈值 `TOPUP_EPS` 只有 **0.009 元**。

于是：

| | 残差 `Δ+low` | 性质 |
|---|---|---|
| 本次误判 | **⟨金额⟩ 元** | 噪声量级 |
| 真实充值 | **A⟨金额⟩元** | 噪声的 40 倍 |

两者走的是同一个 `> 0.009` 门槛 —— **判据无法区分「真信号」和「噪声」**。再叠上 `tierAtLeast` 的 ⟨金额⟩元地板，噪声就被直接兑换成 ⟨金额⟩元主张。

至于**为什么会冒出那 ⟨金额⟩ 的噪声**：第 2 行是全天唯一离群值，触发条件是「停机 84 分钟 + 进程重启」之后的头两次读数不一致（hh:mm:ss 的 A31 可能偏旧），**不是稳态滞后**。这一点仍未证实，见第 12 节末。

## 6. 定量：判定边界离正常工作点只有几分钱

> 本节写于真充值观测之前，「分钟级滞后」那句已被第 12 节推翻；但**余量只有 3.4~8.4 分钱**这个测量本身仍然成立，正是它把根因指向了信噪比。

活动窗口（`away=0`）的 `Δ+low` 实测分布：

```
+⟨金额⟩ ← 误判窗口（唯一正值）
−⟨金额⟩
−⟨金额⟩
−⟨金额⟩
−⟨金额⟩
```

**正常窗口的余量只有 3.4 ~ 8.4 分钱**（对窗口消费而言约 10~20%）。判定阈值 `TOPUP_EPS` 是 0.009 元。

即：决策面距离典型工作点不到 1 角，而输入信号（余额差）存在分钟级到十几分钟级的结算滞后 —— **假阳性不是偶然，是结构性的**。只要有一个窗口的余额还没结算完（`|Δ|` 偏小），而该窗口 `low` 正常为正，就必然触发。

再看比值 `low / |Δ|`：

| 窗口 | low / \|Δ\| |
|---|---|
| hh:mm（误判） | **⟨金额⟩** ← 唯一 >1 的窗口 |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |
| hh:mm | ⟨金额⟩ |

其余窗口整齐地落在 A13~A15 —— 说明 `low ≈ A14|Δ|` 是常态，`Δ+low` 常态就是 −A2 上下。误判窗口只是把这个常态翻转了一次。

## 9. 修复方向（仅登记，本轮未实施，未定稿）

按可行性排序，未做取舍：

> **第 12 节观测后新增（优先级最高）：**
>
> **0. 把门槛抬进信号带。** 观测揭示了一个很好的性质：**真充值的残差 ≈ 充值额本身**。
> 本次 残差 A22 对真值 10；推导上 残差 = Δ + low ≈ 充值额 − (窗口消费 − low) ≈ 充值额 × 0.9~1.0。
> 而噪声残差 ≤ A5。两者差 **40 倍**。
>
> 所以正确的门槛不是 `TOPUP_EPS = 0.009`，而是「**最小档位 ⟨金额⟩元 减去这一窗口可能的估计误差**」（例如 ⟨金额⟩元，或 `0.5 × 最小档位`）。
> 这样做的好处：**不依赖任何时序假设**，不需要先搞清余额读数为什么偶尔偏小，一刀就把噪声和真信号分开了。
> 代价：真正「充 10 但同一窗口花掉 ⟨金额⟩元」的极端情况会漏判 —— 但那时残差 ≈ ⟨金额⟩元，本来就无法与噪声区分，漏判比误判安全。

1. **方向自检**：`topUp > 0` 与 `increase < 0` 同时成立时，要求额外证据（例如 `low` 的置信度、或连续两个窗口的 Δ 累计）。注意不能粗暴要求 `increase > 0`，会漏掉「充 10 花 12」。
2. **改用累计口径**：让 Δ 与 low 在**累计**上比较（README 已确认累计对得上），而不是逐窗比较。例如「今日累计 Δ + 今日累计 low > 档位下限」才认充值。
3. **观测两次再确认**：判出充值时先挂起一个窗口，下一窗口若出现等额的余额回退/未跟随，则撤销。代价是充值的显示延迟一个周期。
4. **用 `topped_up_balance` 对账**：官方直接给充值余额桶，变化量与 `total_balance` 一起看，能绕开消费结算滞后（需先验证该字段的更新时序，本轮只确认它存在且当前为 A25）。
5. **抬高门槛收敛放大**：提高 `TOPUP_EPS`、或对「残差相对窗口消费的比例」设下限。**但这只是把故障概率降低，不改变 5.2 的根因**，不建议单独使用。
6. **可撤销**：给 `baseBalance` 留一个手动/自动的纠正路径（当前一次误判污染一整天且无法回退）。

## 12. 观测结果：真实充值 ¥⟨金额⟩（2026-09-20 hh:mm:ss）

用户实际充值 ⟨金额⟩元。账本第 7 行：

```json
{"t":1789868295075,"dt":300270,"away":0,"model":"deepseek-flash","miss":23562,"hit":3716608,
 "write":0,"out":36379,"calls":33,"extra":0,"noUsage":{},"local":⟨金额⟩,"low":⟨金额⟩,
 "high":⟨金额⟩,"delta":A21,"implied":A7,"topUp":10,"balance":A35,"baseBalance":A38}
```

复算：

```
previous = A26 → total = A35        Δ = +A21
impliedTopUp = A21 + ⟨金额⟩         = +A22
⟨金额⟩ → 不，这次是 A22 > 0.009     → 进充值分支
tierAtLeast(A22)                  = 10          ← 判对
baseBalance A36 → A38
```

### 12.1 第 11 节三个预测的答案

| # | 预测 | 结果 |
|---|---|---|
| a | 到账是否在一次轮询内完成 | ✅ **是**。Δ=+A21 出现在单独一行，= 10 − 本窗口消费 A7 |
| b | 会不会被拆成两次 → 每窗各判 10 → 累计虚高 20 | ✅ **没有发生**。一次到账，判一次 |

### 12.2 结论修正（比原判断更准确）

## 15. 后续缺陷：充值确认延迟把「失效」永久锁死（2026-09-20 由用户发现）

**症状**：只要发生充值，当天的误差指示就变成红色「失效」并且不再恢复。

**根因链（四跳，全都不在锁存逻辑里）**：

```
充值要连续 2 窗才认账   →  那一窗 T 还没更新
                        →  S = max(0, V + T) 少一笔充值，被下限 0 钳住
                        →  E = |S − L| = 当天累计本地消费 L（不是充值额！）
                        →  L ≥ 2 就触发「E ≥ 2 当日锁存失效」
```

关键在钳位：`V + T` 在充值窗口变成很负，被 `max(0, …)` 钳到 0，
于是 `E = |0 − L| = L`。**所以哪怕只充 ⟨金额⟩元，只要当天已花过 ⟨金额⟩元，照样锁死。**

**修法（两项，v4.0.5）**：

1. **pendingTopUp（临时值）**：已看到、未连续两窗确认的台阶，先按整数计入
   `T_显示与算账`，但不计入 `autoTopUp`（持久状态）。且**必须用原始 R**
   而不是滤波后的 M —— M 滞后一窗，救不了到账那一窗。
2. **失效判据加连续窗容错**：由「单窗 ≥ 2 即锁存」改为**连续 3 窗 ≥ 2 才锁存**
   （新增 `errorStreak`）。中间有一窗落回线下就重新计数。

配套：客户端**不再自己抢判失效**（原来有「拿不到宿主机标志位就按当前 E 自判」的兜底，
它比宿主更敏感，会在单窗尖峰上直接变红）。判定权只留宿主一处。

**回归测试**：`v4-account.test.mjs` 情景⑧ 用真实量级（每窗消费 0.5 元）复现，
对照显示旧逻辑在该窗 `E = 3 ≥ 2` 必然锁存；新逻辑全程 `E = 0`。
另外回放断言改成**数据驱动**（不再写死「2 笔、⟨金额⟩元」）—— 用户随手充 ⟨金额⟩元就会让写死的断言假报。
