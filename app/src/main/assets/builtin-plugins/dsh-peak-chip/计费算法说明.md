# 峰谷指示灯 · 计费口径与算法说明

> 状态：**设计说明，未实现**。当前线上是 v4.0.7（5 分钟窗、无边界缓冲、日边界为跨日重置）。
> 本文记录"我们讨论定下来的口径"，以及它与现状的差距。
> 作者：本机 DSH 与用户共同确定（2026-09-20）。

---

## 一、一句话

**用账号余额差算出本日消耗；本地审计只用来"认出充值"；认不准就由用户手动修一次。**

## 二、符号

| 符号 | 含义 |
|---|---|
| `B_t` | 时刻 `t` 读到的账号余额（两位小数） |
| `A` | **当日锚点**：零点之后第一次成功读到的余额 |
| `D_t = A − B_t` | 当日累计余额变化（正 = 钱变少） |
| `L_i` / `Λ_t = ΣL` | 第 i 窗的本机估算消耗 / 当日累计本机估算 |
| `T` | **认定的当日到账累计**（自动识别 + 用户手动修正） |
| `R_t = Λ_t − D_t` | **缺口** |
| `S_t = D_t + T` | **本日消耗**（账号口径，主面板那个数） |
| `M` | 真实"别的客户端花掉的钱"（同账号、如电脑端；面板上归入「无法审计」） |
| `O_t = max(0, S_t − Λ_t)` | 显示用：**无法审计**（旧称「其它端消费」） |
| `E_t = max(0, Λ_t − S_t)` | 显示用：误差 |

## 三、恒等式（整套算法的骨架）

设当日真实的本机消费 `U`、它端消费 `M`、到账累计 `T真`：

```
D = U + M − T真                 （余额差 = 花掉的 − 收到的）
R = Λ − D ≈ T真 − M             （Λ ≈ U）
```

所以 **缺口的物理含义是"到账额减去它端消费"**。两边各自整理：

| 量 | `T` 正确时 | `T` 被污染时（`T̂ = T真 − m`） |
|---|---|---|
| `S` | `U + M` ✅ 精确 | `U + M − m` ❌ 少算 `m` |
| `O` | `M` ✅ 精确 | `M − m` ❌ 少报 |
| `E` | `0` ✅ | `0` ⚠️ **静默** |

**关键性质**：`S` 完全不使用 `Λ` —— 本地计费误差不影响本日消耗，只影响"认充值"这一步。

## 四、参数及来由

| 参数 | 取值 | 为什么是这个值 |
|---|---|---|
| 轮询间隔 | **1 分钟** | ① 日边界要**尽早锚定**（锚点越早，跨零点的充值越可能落进"今天看得见"的情况 b）；② 边界缓冲 Δ 需要细粒度读数才能精确落在 `t+Δ` |
| 计算窗长 `W` | **3 分钟** | **由量化决定，不是由延迟决定**。余额只有两位小数，每分钟典型消费仅 0.022 元 → 1 分钟窗的量化误差占 22%，3 分钟窗降到 7% |
| 边界缓冲 `Δ` | **暂定 3 分钟**（待实测后按"实测 max × 2"定） | 让 `D` 的每个边界读数都包含 `t−L` 之前的全部消费，**与即时的 `Λ` 变成同口径** → 消掉"扣费延迟被认成充值"。只要 `Δ ≥ L`，该项误差为 0 |
| 认充值判据 | 缺口台阶 `ΔR ≥ 0.5` **且该窗余额上升**（`ΔB < 0`） | 充值让余额**上升**，扣费延迟只让余额**不动**；这条与窗长、与延迟无关 |
| 认充值的小误差容许 | **0.4 元** | "本地审计与余额差足够接近"这个前提假设的量级（用来判定该窗是否发生了充值）。**它不是报警阈值** |
| **告警分级阈值** | 黄 `0.6–1.2`、红 `>1.2`、灰（连续 3 天红） | 用户定：**一天的几分几毛计费误差不构成实际损失，不值得报警** → 0.6 起才提示、1.2 以上才算失效。详见 §7.2 |

**实测参数**（2026-09-20 账本，54 个正常窗）：单窗本机消费 p50 = 0.111、p90 = 0.348、峰值 = 1.053 元 → 峰值速率 **0.211 元/分**、中位 **0.022 元/分**。
⚠️ 这些数字随用法变化，是**当时的**速率，不是常数。

### 4.1 认充值的硬规则与两条已知缺口（实现细节，改代码前先读）

- **没有档位表**：官方最低可充 1 元，只假设「整数元」。曾经那张"10 元起、只能整档充"的档位表是错的，
  留着只会把 0.01 元的残差放大成 10 元。
- **中位数滤波**：认账看的是对累计观测量 `R` 做 **3 窗中位数滤波** 后的 `M`（实测噪声 ±0.75，
  而 ¥1 的台阶只有 ~1.0，不滤波分不开）。
- **千万别把 `T` 写成 `round(R)`**：那样 `E = |T − R|` 恒 ≤ 0.5，「无法审计」会被静默吃进 `T`，
  误差行什么都看不见。
- **`away = 1` 的窗要排除出统计**：宿主没在跑，本地账天然为空 —— 老说法是「排除出拟合」。
  如今不做拟合了，这条仍适用于任何"只看本端"的统计。
- **余额结算延迟**：**逐窗对不上**、累计才对得上（实测逐窗差到 ±0.75，50 分钟累计差 1%）。

## 五、窗口与边界规则

### 5.1 窗内边界要缓冲

```
边界 t 的余额读数 := 实际在 t + Δ 读到的值
本窗消耗 = 相邻两个缓冲读数的差
```

**纪律**：算 `R` 时，`Λ` 与 `D` **必须切在同一个读数时刻**。任一边错配，`R` 就会凭空跳一下 → 造出假充值台阶。

### 5.2 日边界：零点重锚，零携带（用户定）

```
锚点 A = 零点之后第一次成功读到的余额（越快越好）
重置   = Λ、D、R、pending、手动充值值、账本 全部归零
携带   = 不跨边界携带任何账，不记录昨天的任何数
```

### 5.3 跨零点的一笔充值：三种落点（本日消耗都正确）

| 落点 | 昨天的账 | 今天的账 |
|---|---|---|
| **(a)** 昨天最后一读之后到账，且**被昨天的窗看到** | `D` 被抵减、`T` 也计入 → 正确 | 锚点已含它 → 正确 |
| **(b)** **锚点之后**到账 | 不影响 | `D` 被抵减 `T`，头两窗认出台阶 → `S = (U−T)+T = U` ✅ |
| **(c)** 昨天最后一读之后、**锚点之前**到账 | `D` 被抵减但没人看到跳变 → **少算 `T`**（已接受） | 锚点已把它吸收 → 正确 |

零点重置的附带好处：**同一笔充值不可能被两天各算一次**（锚点把 `D` 和 `R` 都归零）。

## 六、误差预算（在全部假设成立时）

| 来源 | 上界 | 状态 |
|---|---|---|
| 余额量化（两位小数） | ±0.01 | 物理下限，无法再降 |
| **日边界** | `r × (L + 轮询间隔)`，每天一次、不累积、方向不定 | ✅ **已接受**（峰值约 0.63 元 / 中位约 0.07 元） |
| 单窗归类（充值认到错窗） | `r × |ΔL|` | 不影响总额；靠"只认余额上升"+手动修正兜底 |
| 它端消费 | **0**（它在 `D` 里） | ✅ |
| 赠金到账 / 过期 | 0（按"不问钱怎么没的"处理） | ✅ |
| 掉线（不跨日） | **0**（`D` 是累计量，断开多久都能算回来） | ✅ |
| **充值识别被它端消费污染（静默）** | 每次约 `round(同窗它端消费)`，典型 1 元、恒为**少算** | ✅ **用手动修正兜底**（见 §7.1） |

**两个数不要混**：`0.4` 是"认充值"这一步的**前提假设**（假设不成立时充值会认错，那属于预期内、由手动修正兜底）；`1.0` 是**报警线**（只对"手动填对之后仍存在的未解释缺口"报警）。

## 七、失败模式与操作纪律

### 7.1 充值识别错误（预期内、不可解，**不算失效**）

**发生条件**：充值到账那一窗，同账号别的客户端也在花钱且 ≥0.5 元。

**原因**：`ΔR = T − m` 被四舍五入成整数 → `T̂ = round(T − m)` → 少算 `round(m)`。

**为什么静默**：`O` 与 `E` 都拿"认定值"去比同一个缺口 —— **等于用 T 校验 T**。

**为什么它不算插件失效**：这是"用本地审计去认整数充值"这件事的固有精度极限，**不可能靠算法解决**。处置方式是人工的：

> **纪律**：每次充值后核对一眼「今日充值」是否等于实付金额（填的是**到账额**，不是支付额——有赠送时两者不同）。

**提交预览（v4.1.4，只影响显示）**

客户端提交手填值时，同一次 `mutate` 里还会写一个**严格递增**的 `previewNow` 时间戳；宿主看到它就**单独取一次余额**（多一次 `GET /user/balance`），用 `previewTotals()` 算出一组数字写进 `preview*` 字段：

| 字段 | 含义 |
|---|---|
| `previewAt` | 本轮预览的请求时间（> 0 = 预览有效） |
| `previewSampleAt` | "单独取到余额"的时间；**0 = 没取到** |
| `previewTopUp` | 刚提交的充值额（手填优先；清除手动值后 = 自动累计） |
| `previewBalance` / `previewDayFirst` | 这次单独采到的余额 / 当日锚点（还没锚点时用这次采样当锚点） |
| `previewTodaySpent` | `S' = max(0, V' + T')` |
| `previewOtherSpent` | `O' = max(0, S' − L)` |

面板在 `previewAt > 0` 期间用这组数**顶替显示**（界面上带 `*`），下一窗正常算账成功后宿主把它们清掉（`previewAt = 0`）—— 从那一刻起显示的又是正式值。

**面板上的两段（别混）**

| 显示的来源 | 谁给的 | 什么时候用 | 界面标记 |
|---|---|---|---|
| ① 本地回声 | **客户端**（`topUpEcho`） | 点确认那一刻起，到宿主确认（预览送达/正式认领）为止 | `*` + 「已提交，正在确认」 |
| ② 宿主预览 | 宿主 `preview*` 字段 | ① 撤销后、下一窗正式算账之前 | `*` + 「已提交，等下一窗确认」 |
| ③ 正式值 | 宿主正常窗 | 正常窗跑完（宿主清掉 `previewAt`） | 无 |

优先级：**① > ② > ③**。① 只回显"刚提交的那个数"（不重算任何量），它的存在就是为了让
"填多少、确认后就是多少"成立 —— v4.1.4 只有 ② 时，确认后客户端会先拿**还没更新的快照**
重画一次，于是数字先回跳成旧值、约 1 秒后才跳上来（用户报障原话：谁家手动填值是这样来回跳的）。

三条硬约束（改之前先读）：

1. **这组字段不参与记账**：不进 `accountDay`、不动 `rHistory`（中位数滤波）、`stepStreak`（台阶确认）、告警锁存。手动提交**不会**触发一个临时窗口 —— 那会在滤波里插一个不规则采样点，还会把台阶确认往前推（宁可慢 1~2 秒，也不动账）。
2. **不许有第二份口径**：`S'` / `O'` 与正常窗共用 `accountTotals()` 与 `splitResidual()` 两个函数（`tests/v4-preview.test.mjs` 有一条"预览与正常窗同源"的断言盯着）。v4.0.6 那次故障就是两边各写一份口径。
3. **取不到余额也不许编数**：采样失败时只顶替手填的那一个数（`previewSampleAt = 0`，余额/`S` 保持原值），等下一窗的正式值。

**关键性质**：**手动填对之后，这项误差就从失效指示里彻底消失。**

```
R = T真 − M + ε
E = max(0, R − T) → 填对 T 后 = max(0, ε − M)
```

`m`（同窗它端消费）整个从 `E` 里出局 —— 它只影响过"识别那一笔"，而手动值是**覆盖**语义（会把之前的自动识别值丢掉）。

### 7.2 三档告警（本次定稿）

判据只有一处：`E = max(0, R − T)`，**前提是"今日充值已按实付核对"**（否则它分不清"你没修"和"真失效"）。

| 级别 | 触发条件 | 恢复 | 物理含义（峰值速率 0.211 元/分、Δ=3 分钟下的等价延迟） |
|---|---|---|---|
| 正常 | `E < 0.6` | —— | 在容许内 |
| **黄色 · 存疑** | `E ∈ [0.6, 1.2]` **连续 3 窗** | ✅ **可恢复** | 延迟超出 `Δ` 约 2.8 分钟（合计 ≈5.8 分钟），或本机多算累积到这个量 |
| **红色 · 失效** | `E > 1.2` **连续 3 窗** | ❌ **当日锁存，跨日复位** | 延迟超出 `Δ` 约 5.7 分钟（合计 ≈8.7 分钟） |
| **灰色 · 故障** | **连续 3 个自然日**都触发过红色 | ❌ **永久，不再恢复** | 不是偶发，是持续性问题 |

**状态机**（三档统一用"连续 3 窗"防抖）

```
正常 → 黄    E ≥ 0.6  连续 3 窗
黄   → 正常  E < 0.4  连续 3 窗        ← 0.4–0.6 是滞回带，防抖动闪黄
正常/黄 → 红 E > 1.2  连续 3 窗         ← 只升不降；当天红了就不回黄
红         当日锁存（跨日复位）
红 × 连续 3 个自然日 → 灰               ← 永久，无自动出口
跨日：清掉 黄/红 的当日锁存；**红日计数必须保留**
```

**灰的出口只有一个（有意设计）**：**手动升级插件并把 `RULE_VERSION` 升版** —— 迁移会一次性清掉全部告警状态（含红日计数与 `grayAt`）。
灰色告警的语义是"这套计费口径已经不成立了（例如官方改了定价规则或计费档）"，而我们不是官方，**做不出能自更新的插件**，所以它就该一直亮着，直到有人真的去改代码。

**需要持久保存的告警状态**（跨日**不清**）：`alertLevel`、`yellowStreak`、`redStreak`、`redDayStreak`、`lastRedDayKey`、`grayAt`。

> ⚠️ **这些不属于"账本"。** §5.2 说的"零点清掉前面所有账本"**不能清它们** —— 清掉红日计数，灰色告警永远触发不了。

**判定权**只有宿主一处（客户端不拿瞬时值自己判，避免抢跑）。

**它越线只可能说明两件事**（都不是充值识别错误）：

| 可能 | 含义 |
|---|---|
| **本机多算**（`ε > 0`） | 本地审计系统性高于实际计费：定价档算错、重复计费、缓存计费口径不对 |
| **余额还没扣到** | Λ 已记、`D` 未跟上 → 延迟超出 `Δ` |

**连续 3 窗把两类东西分开**：延迟抖动是单窗尖峰（扣费一落地就归零），本机多算是单调累积（必然连成片）→ 只有后者会被判失效。

**★ v4.0.8 的意外收获：原来"抓不到的两类"现在抓得到了**

引入"认充值必须**该窗余额上升**"之后，台阶检测不再能吸收那两类失效：

| 失效 | 现在的行为 |
|---|---|
| 系统性本地多算（渐进式） | `Λ` 涨、`D` 按**真实**用量跌 → 余额是**下降**的 → `balanceRose=false` → **不许认充值** → 缺口留在 `E` 里 → 连续 3 窗越线就会变黄/变红 ✅ |
| 平台延迟严重（批量结算） | 延迟期余额**不动**（不是上升）→ 同样不许认充值 → `E` 涨；批量落地后 `E` 回落 → 黄可自动恢复 ✅ |

也就是说：**这盏灯从"只测残差"升级成了"也测被吸收掉的那部分"** —— 因为吸收的前提（余额上升）被显式要求了。

**现在剩下的唯一静默项**是 §7.1 那条（充值到账那一窗同时有它端消费/大批扣费，导致整数认定偏 1）——
它属于预期内、由手动修正兜底。补充手段仍是 **"自动识别充值 vs 你实际支付的充值"的对照显示**。

**与现状的关系**：`errorLatched`（当天锁存 0/1）与 `errorStreak` 被这三档取代；`RULE_VERSION` 从 **407 升到 408**（复用已有的口径迁移机制，一次性清掉旧告警状态）。

**已定的边界（本次收口）**

| 项 | 定论 |
|---|---|
| 黄进出阈值 | 进 `≥0.6`、出 `<0.4`，均连续 3 窗 → `0.4–0.6` 是滞回带 |
| 连续窗数 | **三档统一 3 窗**（不做"越严重越快"的快通道） |
| 灰的触发 | **连续 3 个自然日都触发过红**，不附加其它条件 |
| 灰的恢复 | **永久，无自动出口**；出口只有"手动升级插件 + `RULE_VERSION` 升版" |
| 偶发凑成灰的风险 | **接受**：判为概率过低，纯偶然的极端情况不设计 |

> 注意"连续"的定义：某一天**完全没有数据**（插件整天没跑）不算红日，连续计数会**重置** —— 连续就是连续。

### 7.3 其它已接受项

- 昨天在情况 **(c)** 会少算一笔充值 —— 因为不跨日记账；
- 赠金过期会让 `R` 的基线**永久下移一次**，之后不再回到 0 → **任何人不得再用 `|R| < 某值` 当健康判据**；
- **换账号 / 换 key 不考虑**（基准会失效，直到跨日重置）。

## 八、待验证的假设（唯一的未验证前提）

**"平台余额刷新延迟 `L` 有上界"** —— 目前**没有任何来源**：
- 官方文档只规定了模型调用的并发数（429），[余额接口](https://api-docs.deepseek.com/zh-cn/api/get-user-balance/) 与 [限速页](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/) 都没有延迟或频率承诺；
- 现有账本只能证明"5 分钟分辨率下看不见延迟"（0 个"本地花了而余额没动"的窗），**证明不了上界**。

**验证方法（受控实验，零凭据成本）**：
1. 本机产生一次孤立、明显的消费（约 0.1–0.5 元），记下本机完成时刻 `t0`；
2. 之后每 15–20 秒查一次余额，记下**第一次下跌的时刻** `t1`；
3. 换不同金额、不同时段重复 3–5 次 → 得到 `L` 的分布（min/p50/max），顺带确认有没有 429。

拿到分布后：`Δ = max × 2`；并把本文 §6 的假设行改成实测值。
